# CRITICAL

### C1. `GET /reports/list/teachers` всегда возвращает 500

- **Где:** `my_serve_chat_test/repositories/reports/reportsRepository.js:1,46`
- **Суть:** строка 46 вызывает `sqlUserAccountingName('u')`, но строка 1 импортирует только
  `sqlUserAccountingNameOrEmpty`. Функция `findReportAuthors` падает с
  `ReferenceError: sqlUserAccountingName is not defined` до любого SQL.
- **Чем грозит:** фильтр по преподавателям в списке отчётов у суперпользователя не работает
  никогда. Клиент показывает «Сервер не поддерживает список преподавателей. Обновите backend»,
  что уводит диагностику в ложную сторону. `node --check` это не ловит (ошибка не синтаксическая),
  ни один smoke этот эндпоинт не трогает.
- **Фикс:** добавить `sqlUserAccountingName` в импорт строки 1.
- **Подтверждение:** `запуск` — вызвал `findReportAuthors` со stub-БД, получил `ReferenceError`;
  `findReportsList` в том же модуле собирается нормально.

### C2. `PUT /reports/:id` с `content` удаляет все занятия и начисления отчёта и отвечает 200

- **Где:** `my_serve_chat_test/controllers/reportsController.js:746-766, 831-834`;
  `services/reports/reportHelpers.js:21`
- **Суть:** обновление сначала удаляет `lesson_income`, `transactions` и `lessons` старого отчёта
  (746-762), и только потом, если `slots` не переданы, парсит `content`. Но
  `buildReportContentFromSlots` пишет строки как `14:00-16:00 Иван 2.4`, а `parseReportContent`
  принимает только часовой формат (`^(\d{1,2})-(\d{1,2})\s+(.+)$`) — для slots-контента возвращает
  пустой массив. Итог: занятия удалены, новые не созданы, отчёт с текстом остался, ответ 200.
- **Чем грозит:** ученики перестают биллиться, доход преподавателя за день становится нулём,
  UI не показывает ошибку. **Важно:** текущий UI сохраняет отчёты только структурированно
  (`updateReportStructured`), текстовые `createReport`/`updateReport` в `reports_service.dart`
  не вызываются ниоткуда — то есть путь достижим через API напрямую (и валидатор его разрешает:
  `validateReportInput` принимает `content` без `slots`), а не через приложение.
- **Фикс:** научить `parseReportContent` формату `HH:MM-HH:MM` и отклонять пересборку (409/400),
  если отчёт с занятиями распарсился в ноль занятий.
- **Подтверждение:** `запуск` — `parseReportContent(buildReportContentFromSlots(...))` вернул `[]`.

### C3. Парсер цены в тексте отчёта завышает суммы

- **Где:** `my_serve_chat_test/services/reports/reportHelpers.js:34-41`
- **Суть:** `const price = priceInt * 1000 + priceDec * 100;` — дробная часть умножается на 100
  независимо от числа знаков.
- **Чем грозит:** `2.45` → **6500 ₽** вместо 2450; `1.05` → **1500 ₽** вместо 1050. Пишется
  неверная `lessons.price`, неверное списание с баланса ученика и завышенное начисление 50%
  преподавателю. Верхней проверки цены нет, поэтому ничто не поймает это на входе.
- **Фикс:** `parseFloat(`${int}.${dec}`) * 1000` + проверка правдоподобного диапазона цены.
- **Подтверждение:** `запуск` — `parseReportContent('... 14-16 Иван 2.45 / Мария 1.05')` вернул
  `price: 6500` и `price: 1500`.

### C4. `POST /students/link-existing` — привязка к любому ученику по id

- **Где:** `my_serve_chat_test/controllers/studentsController.js:452-500`;
  `routes/students/studentRoutes.js:21`; `routes/students.js:14`
- **Суть:** эндпоинт защищён только `authenticateToken` + `requirePrivateAccess`. Единственная

  падает на баланс атакующего.
- **Фикс:** требовать существующее отношение (инвайт/согласие) или роль суперпользователя,
  и отдавать только неперсональные поля.
- **Подтверждение:** `код` — прочитал контроллер и цепочку роутеров целиком.

### C7. Аудит пишется во втором соединении внутри открытой транзакции — риск полного deadlock

- **Где:** `my_serve_chat_test/utils/accountingAudit.js:14`; `db.js:74-80`; 17 из 18 вызовов
  `logAccountingEvent` в `reportsController.js`, `studentsController.js`, `lessonsController.js`,
  `transactionsController.js`
- **Суть:** `const db = client || pool;` — и `client` передаёт только один вызов
  (`reportsController.js:1085`). Все остальные держат соединение внутри `BEGIN` и берут из пула
  **второе**. Пул создан как `new Pool({ connectionString, ssl })` — без `max` (дефолт pg = 10)
  и без `connectionTimeoutMillis` (дефолт 0 = ждать вечно).
- **Чем грозит:** 10 одновременных бухгалтерских записей (обычная картина при вечерней сдаче
  отчётов) держат все 10 соединений и все ждут одиннадцатого, которого не будет. Пул встаёт
  навсегда, вместе с ним весь бэкенд, включая чат. Вторичный эффект: аудит-строка коммитится
  независимо, поэтому откатанная операция остаётся в журнале как выполненная.
- **Фикс:** передавать `client` во все вызовы (`logAccountingEvent` уже изолируется `SAVEPOINT`)
  и задать `max` + `connectionTimeoutMillis` пулу.
- **Подтверждение:** `код` — проверил конфиг пула и все места вызова.

### C8. Разбор суммы из банковской выписки теряет тысячи и превращает расходы в депозиты

- **Где:** `my_serve_chat_test/controllers/bankStatementController.js:211-224`
- **Суть:** `cleaned.replace(',', '.')` заменяет только **первую** запятую, а результат затем
  прогоняется через `Math.abs`.
- **Чем грозит:** `"1,234.56"` → `parseFloat("1.234.56")` → **1.234 ₽** вместо 1234.56 (в 1000 раз
  меньше); `"1,234,567.89"` → тоже 1.234. Отдельно: снятие знака превращает каждую расходную
  строку выписки (комиссии, переводы наружу) в положительный депозит ученику.
- **Фикс:** определять десятичный разделитель по последнему `.`/`,` после удаления разделителей
  групп; сохранять знак и исключать отрицательные строки.
- **Подтверждение:** `запуск` — получил `1.234` для `"1,234.56"`.

# HIGH

### H1. `is_late` не пересчитывается при смене даты отчёта

**Где:** `reportsController.js:496-502` (создание) vs `812-828` (обновление).
При создании `is_late` считается как `($1::date < $4::date)`; при обновлении — комментарий
«при редактировании не пересчитываем». Значит: создать отчёт на сегодня (`is_late = false`),
затем `PUT` с любой прошлой датой — и отчёт, который никогда не сдавался вовремя, считается
вовремя. Он попадает в `income_counted`/`salary` и получает `lesson_income` через
`syncReportLessonIncome`. Обходится вся дисциплина дедлайнов и привилегия `set-not-late`
(суперюзер), доход задним числом заходит в уже закрытый месяц.
**Фикс:** пересчитывать `is_late` при смене `report_date`, объединяя по `OR` с сохранённым
значением. `код`

### H2. Пересборка отчёта разрывает связь пропуск→отработка, позволяя списать один пропуск дважды

**Где:** `reportsController.js:759-762, 889-905`; `migrations/add_lesson_status_and_makeup.sql:5`.
Правка старого отчёта удаляет его `missed`/`cancel_same_day` и вставляет новые строки с новыми id.
`origin_lesson_id` в уже записанных отработках других отчётов имеет `ON DELETE SET NULL` → обнуляется.
Guard `alreadyMakeup` и запрос «неотработанный пропуск» перестают видеть связь, и тот же пропуск
снова становится доступен для платной отработки. `код`

### H3. Отработка без уникального индекса — двойное списание в гонке

**Где:** `lessonsController.js:49-61, 286-289`. Проверка «уже отработано» — обычный SELECT;
advisory lock построен на `user:student:date:time`, то есть этот случай он не сериализует.
Уникального индекса на `(origin_lesson_id) WHERE status='makeup'` в миграциях нет. Два
параллельных `createLesson` с одним `origin_lesson_id` создают два платных занятия. `код`

### H4. Частичный `PUT /students/:id` сбрасывает `pay_by_bank_transfer` и обнуляет контакты

**Где:** `studentsController.js:519-556`. `payByBank` вычисляется как
`pay_by_bank_transfer === true || === 'true'`, то есть отсутствие поля даёт `false`, и это пишется
безусловным `SET`. `salaryRules.js` вычитает `BANK_TRANSFER_LESSON_DEDUCTION = 300` из базы
зарплаты только при `true` — значит правка имени навсегда поднимает выплату на 150 ₽ за каждое
будущее занятие. Тот же запрос перезаписывает `parent_name`/`phone`/`email`/`notes` в `null`.
**Фикс:** собирать `SET` только из фактически присутствующих ключей. `код`

### H5. Депозит без `target_teacher_id` засчитывается полностью каждому преподавателю

**Где:** `studentsController.js:811-825` (та же формула в `71-84`, `875-886`).
Условие `(target_teacher_id = $2 OR target_teacher_id IS NULL)` означает: непривязанный депозит
виден как свой каждому. Ученик, оплативший 10 000 ₽ и занимающийся у двух преподавателей,
показывает +10 000 ₽ обоим, а списываются только свои занятия. Под 10 000 ₽ оплаты можно провести
20 000 ₽ занятий, и `createLesson` баланс не проверяет вообще. `код`

### H6. Баланс ученика считается двумя разными формулами

**Где:** `studentsController.js:798-806` (супер: `SUM(deposit) - SUM(все занятия)`) vs `811-825`
(преподаватель: свои занятия + непривязанные депозиты). Экран преподавателя и экран бухгалтерии
показывают несводимые числа для одного и того же ученика, единого авторитетного баланса нет. `код`

### H7. `DELETE /students/:id/full` каскадом уносит финансовую историю всех преподавателей

**Где:** `studentsController.js:730-760`; `migrations/add_students_tables.sql:20,33`.
Эндпоинт корректно ограничен суперпользователем (`403` иначе) — это не дыра в правах, а
отсутствие предохранителей: `lessons.student_id`, `transactions.student_id`,
`report_lessons.lesson_id` — все `ON DELETE CASCADE`. Один вызов необратимо стирает все депозиты,
все списания и все строки отчётов по ученику **у всех** преподавателей, без проверки наличия
транзакций и без суммы в аудите (`payload: { bySuperuser: true }`). При этом
`teacher_balance_transactions.lesson_id` — `ON DELETE SET NULL`, поэтому начисления зарплаты
остаются с висящим `lesson_id`, а `deleteLessonIncomeForLesson*` ищут именно по `lesson_id` и
вычистить их уже не могут. `код`

### H8. Самоудаление аккаунта каскадом уносит бухгалтерию

**Где:** `authController.js:836`; `routes/auth.js:62`; `migrations/add_students_tables.sql:12,20,26,33,38`.
`DELETE /auth/user/:userId` (единственная дополнительная проверка — пароль) удаляет строку `users`,

удаление этих учеников каскадит дальше в занятия и транзакции **других** преподавателей. Наличие
бухгалтерских строк не блокирует и даже не помечает удаление. `код`

### H16. `lesson_date` уезжает на день назад, если процесс Node работает не в UTC

**Где:** `lessonsController.js:126-139, 169` (`SELECT l.*`); `lib/models/lesson.dart:98`

предыдущим днём. Показательно, что соседние поля в том же запросе сервер отдаёт как
`origin_lesson_date::text`, а отчёты вообще идут через `to_char` + `parseCalendarDate` — то есть
опасность известна, но на этот путь не распространена.
**Подтверждение:** `запуск` — `getTypeParser(1082)('2026-06-15')` под Moscow TZ даёт
`2026-06-14T21:00:00.000Z`. Проявление — `окружение` (зависит от `TZ` процесса; в конфигах
деплоя `TZ` не задан).

# Покрытие проверок

| Проблема | Детали |
|---|---|
| Ни один бухгалтерский smoke не запускается без живой БД | Все 11 скриптов открывают `pool` из `db.js` и сидируются из существующих строк (`loadUsers`, `teacher_students`). `npm run smoke:all` требует базу с суперпользователем, преподавателем с приватным доступом и связями — в CI недоступно, между окружениями невоспроизводимо |
| Контракт прав отчётов молча скипается | см. H29 |
| `smoke-teacher-balance` скипает обе содержательные проверки | `smoke-teacher-balance.js:84,110` — при отсутствии данных остаётся только `typeof balance === 'number'`, что проходит и при неверном балансе |
| Параллельный двойной submit проверен для занятий, но не для отчётов | `smoke-accounting-edge-cases.js:60-73` действительно параллелит `createLesson`; `smoke-accounting-reliability.js:154-175` вызывает `createReport` дважды **последовательно** с одним ключом — это тест replay, а не гонки |
| XLSX-smoke не проверяет ни одной суммы | `smoke-accounting-xlsx.js:68-117` — только имена листов, заголовки, статус и суффикс файла |
| `node --test` не содержит ни одного бухгалтерского файла | все 8 тестов — звонки/пуши/realtime |

**Сценарии без покрытия вообще:** параллельное создание отчёта; матрица прав на удаление
(чужой `DELETE /reports/:id`, `DELETE /students/lessons/:id`, `DELETE /students/transactions/:id`,
`DELETE /students/:id/full`); баланс ученика и начисление преподавателя после правки отчёта;
числовая корректность CSV/XLSX против фикстуры; эквивалентность `/export` и `/export-xlsx` за один
период; сводимость `SUM(teacher_balance_transactions)` с `/reports/salary`; контракт
«`DECIMAL` приходит строкой»; `GET /reports/list/teachers` (именно поэтому C1 и выжил).

**Что стоит сделать в первую очередь:** вынести чистые функции (`salaryRules`, FIFO-распределение,
`computeReportIncomeAmount`, сериализаторы) в `node --test` с фикстурами — это покрывает большую
часть денежной математики без БД.
